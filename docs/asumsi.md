Label: [Dari dokumen klien], [Asumsi], [Usulan], [Belum diketahui]. Bila spesifikasi dan prompt stage bertentangan, prompt stage menang dan konfliknya dicatat di bagian 1. Stage berikutnya menambah entri di akhir tiap bagian.

## 1. Konflik antara spesifikasi dan prompt (prompt menang)

- K-01 [Asumsi] Jumlah barang. Spesifikasi (Bagian 2 dan P-05) menyebut sekitar 3.500 barang; proposal, RAB, dan prompt menyebut 3.600 SKU. Dipakai 3.600 untuk data contoh dan uji performa.

- K-03 [Asumsi] Aplikasi mobile. Spesifikasi (Bagian 2 dan 5) menyebut Monitoring Owner berupa PWA hanya lihat dengan 5 layar (OWN-01 sampai OWN-05) dan tanpa layar Sales. Mockup HTML menampilkan keduanya pada 360 x 800; layar OWN-06 dan SALES tidak punya wireframe di spesifikasi dan dirancang dengan token yang sama.
- K-04 [Asumsi] Peran. Spesifikasi memuat Owner, Supervisor, Kasir. Prompt menambah Frontliner. RAB 4.1 memakai istilah Admin. Dipakai: Owner, Supervisor, Kasir, Frontliner; istilah Admin pada RAB dipetakan ke Supervisor.

## 3. Perkakas

- R-01 [Asumsi] Node.js 22.12.0 atau lebih baru: batas paling ketat dari field engines paket terpasang (vitest dan @axe-core/playwright). Field engines di package.json diisi sesuai.
- R-02 [Asumsi] Versi paket dikunci package-lock.json hasil npm install --save-exact tanpa nomor versi yang ditulis manual. Versi terpasang dilaporkan lewat npm ls.
- R-03 [Asumsi] Pemecahan chunk memakai build.rolldownOptions.output.codeSplitting milik Vite terpasang (berbasis Rolldown). Bila Vite diganti ke versi berbasis Rollup, ubah menjadi build.rollupOptions.output.manualChunks.
- R-04 [Asumsi] Hanya Chromium yang dipasang untuk Playwright (tablet Android dan PC Windows memakai mesin Chromium). Firefox dan WebKit menyusul bila diperlukan.
- R-05 [Asumsi] src/main.ts memuat router hash dan dynamic import; hanya modul portal yang ada pada Stage B dan aplikasi lain ditambahkan pada stage berikutnya. playwright.config.ts dan tes e2e pertama dibuat pada Stage B. npm run test memakai passWithNoTests.
- R-06 [Asumsi] Lingkungan Vitest adalah node karena jsdom dan happy-dom tidak ada dalam daftar dependensi dev yang diizinkan. Perilaku DOM diuji lewat Playwright.
- R-07 [Asumsi] src/styles/tokens.css, export/app_tokens.dart, public/fonts, dan public/icons dibangkitkan oleh npm run tokens dan npm run assets; jangan diedit manual. public/fonts dan public/icons tidak masuk git. Berkas Dart memerlukan Dart 3 (modifier abstract final).
- R-08 [Asumsi] lint:teks tidak memeriksa folder spec, public (lisensi pihak ketiga), node_modules, dan dist.
- R-09 [Asumsi] base Vite bernilai ./ agar build dapat dipasang di subfolder. Routing hash tidak terpengaruh.
- R-10 [Asumsi] @types/node tidak dipasang karena tidak ada dalam daftar dependensi dev yang diizinkan, sehingga vite.config.ts tidak memakai modul Node. Berkas scripts adalah JavaScript biasa dan tidak diperiksa tipe.

## 15. Revisi POS putaran ketiga (11 November 2026)

- R3-01 [Dari dokumen klien] Ukuran layar acuan klien sekitar 1366 x 640 px (area halaman pada gambar 1). Syarat "tanpa scroll bar" pada modal barang, modal Pembayaran N, dan semua tab pembayaran diuji pada 1366 x 640, 1280 x 720, 1280 x 800, dan 1366 x 768. - R3-03 [Usulan] Batas jual adalah stok Toko (`stock.display`). Stok kosong menolak barang masuk keranjang dengan peringatan; jumlah di keranjang juga tidak boleh melebihi stok Toko (pesan "Stok toko ... hanya tersisa ..."). Stok negatif dari POS tidak mungkin lagi. Bill lama yang dipanggil dengan jumlah di atas stok (stoknya terjual di pesanan lain saat bill ditahan) masih bisa dipanggil, dibayar, atau dikurangi; keranjang menandainya "Stok kurang" dan layar bayar menampilkan peringatan stok, tetapi pembayaran tidak ditolak. Alasannya: stok negatif sudah punya alur Ditinjau di Back-Office, dan Open Bill contoh (B-0002 untuk persetujuan piutang dari HP) memang memuat jumlah di atas stok toko; menolak pembayaran akan mematahkan alur itu. Pertanyaan terbuka untuk klien: apakah Open Bill lama harus ikut diblokir.
- R3-04 [Usulan] Pecahan uang Tunai: pecahan pertama adalah lembar tunggal terkecil (1.000, 2.000, 5.000, 10.000, 20.000, 50.000, 100.000) yang lebih besar dari total, atau kelipatan 50.000 berikutnya bila total sudah 100.000 ke atas; pecahan kedua adalah kelipatan 50.000 berikutnya yang lebih besar dari pertama. Cocok dengan empat contoh klien (3.500, 8.000, 141.000, dan 110.000 pada gambar 3).
- R3-05 [Perubahan atas R2-09] Non-tunai pada pembayaran hanya QRIS, Transfer, dan EDC: kanal (Gopay, OVO, Shopee Pay, BCA, BRI, Mandiri) dan layar Scan QR dihapus dari alur bayar. QRIS dikonfirmasi manual oleh kasir. Isian Nomor Referensi diganti kolom Catatan. Pilihan kanal pada modal Retur tidak disebut dokumen dan dibiarkan seperti putaran kedua (pertanyaan terbuka untuk klien).
- R3-06 [Usulan] Catatan pembayaran satu kolom bersama semua tab. Pada tab Non-Tunai tampil di bawah pilihan (seperti gambar 4); pada tab lain tampil di baris bawah bersama tombol Kembali dan Bayar supaya semua tab muat satu layar. Maksimal 144 karakter, tersimpan pada `Sale.note`, tampil di Riwayat dan pada struk.
- R3-07 [Usulan] Diskon nominal berlaku per satuan barang (potongan dikali jumlah). Batas: tidak lebih dari harga satu satuan; persen paling banyak 100. Data bangkitan rincian invoice disesuaikan (selisih pembulatan dipotong dari satu satuan pada baris terpisah) supaya jumlah invoice tetap sama persis.
- R3-08 [Usulan] Diskon Transaksi memakai hak akses Diskon yang sama dengan diskon baris (Owner dan Supervisor langsung, Kasir dengan PIN, Frontliner tidak melihat menunya). Diskon harus menyisakan total di atas nol (persen di bawah 100, nominal di bawah subtotal) karena transaksi Rp 0 tidak bisa dibayar. Diskon ikut tersimpan pada Open Bill dan pada `Sale.discount`; nilai retur dikurangi secara proporsional. Pada Merge Bill diskon bill tujuan dipertahankan dan diskon bill sumber tidak ikut digabung (kasir diberi tahu lewat pesan). Pada Split Bill diskon persen ikut ke kedua bill, sedangkan diskon nominal dibagi sebanding subtotal (sisa pembulatan ke bill baru) agar jumlah potongan tetap dan tidak ada bill bertotal Rp 0. - R3-09 [Usulan] "Mulai Pesanan Baru" selalu meminta konfirmasi (juga bila keranjang kosong). Frontliner tetap memiliki "Cetak Struk Draf" sebagai pilihan keempat menu titik tiga karena tidak punya tombol Bayar.
